HiveVision

Point a Limelight 3A at the field, get game-element positions in field coordinates, and route autonomous paths around obstacles. Built for FTC.

Install

Add the repository and the one dependency to your TeamCode/build.gradle:

repositories {
    maven { url = uri("https://sidhuharjas.github.io/hvtest") }
}

dependencies {
    implementation "org.hivevisionftc:core:2.0.0"
}

Sync, and you're done. One artifact carries everything: perception, field projection, and obstacle-avoiding route planning.

Upgrading from 1.x: delete your org.hivevisionftc:weaver line — route planning now lives inside core. Keeping both on the classpath causes duplicate classes.

Quickstart

1. Set up Constants

Every per-robot number lives in one editable file: Constants.java — copy it into TeamCode, measure your camera mount (see Calibration), and paste your model's labels.txt names. Then build a Navigator from it:

Navigator navigator = Constants.createNewNavigator(hardwareMap);
navigator.setPoseSource(() -> new FieldPose(
        follower.pose().x(), follower.pose().y(), follower.pose().heading()));

Tracking uses model label names, not enums — next season you edit TRACKED_CLASSES and MODEL_LABELS in that one file, nothing else.

2. The basic loop

Update once per loop; ask for the closest target or a full route:

while (opModeIsActive()) {
    follower.update();
    navigator.updateVision();                  // read camera, project onto the field

    if (navigator.didDetect()) {
        Detection ball = navigator.closest();  // nearest element, or null
        telemetry.addData("Element", ball.getClassName());

        PathResult route = navigator.returnPath();   // obstacle-avoiding Weaver route
        if (route != null && !follower.isBusy()) {
            follower.follow(PedroPathingConverter.toPath(route));
        }
    }
    telemetry.update();
}

returnPath() returns null when nothing was detected — always null-check. PedroPathingConverter is built into Marrow core itself, not Pedro:

import com.skeletonarmy.marrow.weaver.PedroPathingConverter;

3. Advanced: refine the plan (all optional)

Everything extra is a fluent call chained before returnPath():

navigator.updateVision()
        .track("red_nectar", "blue_nectar")    // model labels, not enums
        .maxObjects(2)                         // visit at most 2 elements
        .clearance(6.0)                        // inches kept from obstacles
        .sort(Sort.SIZE)                       // SHORTEST, LONGEST, SIZE, CONFIDENCE, COLOR, NONE
        .avoid(new CircleZone(new Point(72, 72), 18.0));

PathResult route = navigator.returnPath();

Zones persist across loops — add them once at init (clearZones() resets). The full 1.x surface is still available through navigator.vision() (the HiveVision session) and navigator.detections() (the DetectionList with clampYDetections, with(...), and the rest).

Run the examples

Ready-to-run files ship in docs/examples/:

FileWhat it does
Constants.java The one file you edit: camera mount, labels, hardware name, pathing defaults.
AutoBallHuntOpMode
"HiveVision Navigator Auto"		 One-shot autonomous. Detects targets, builds a Weaver route through the closest 2, drives it.
ManualBallChaseOpMode
"HiveVision Loop with Obstacles"		 Runs a detection loop the whole match. Re-plans around an obstacle whenever the robot is idle.
  1. Copy the OpMode plus Constants.java and SampleFollowerFactory.java into your TeamCode module (they already declare package org.firstinspires.ftc.teamcode).
  2. Edit Constants.java for your camera mount, labels, and hardware name — the Limelight is expected under "limelight" unless you change LIMELIGHT_NAME.
  3. Build and deploy TeamCode to the robot the way you normally ship code.
  4. On the Driver Station pick Autonomous → HiveVision Navigator Auto (or the loop one), turn on the Limelight, press start.

Telemetry shows what it sees: closest element label, field X/Y, and route status. If it says “No targets detected”, check the Limelight pipeline index and that the game elements are inside the camera view.

Calibration

Distance estimation comes from your camera geometry. Measure these once, write them into Constants.java, and positions on the field will line up:

ConstantWhat to measure
CAM_HEIGHTFloor to lens center (inches)
BALL_HEIGHTFloor to game element center (inches)
CAM_PITCH_DEGTilt below horizontal (degrees)
CAM_X_OFFSETLens forward of robot center (+ forward)
CAM_Y_OFFSETLens left of robot center (+ left, − right)
MIN_CONFIDENCELowest confidence you trust (0.0–1.0)
MAX_STALENESS_MSHow old a detection may be (ms)
If your robot is in CAD, pull the four geometry values from the assembly — it beats a tape measure. Then double-check on the real robot for tile compression and mount flex.

Full measurement procedure and coordinate frames: docs/calibration.md. API reference: docs/MODULES.md. Example OpModes: docs/examples/.

Build from source

Clone sidhuharjas/hvtest, then:

./gradlew test           # unit tests, no camera needed
./gradlew spotlessApply  # format
./gradlew assembleRelease

Every push of a v* tag (or a manual run of the Publish to Pages Maven repo workflow) rebuilds the AARs and republishes them to this site. Bump version in build.gradle.kts before tagging.
